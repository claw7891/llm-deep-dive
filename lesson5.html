Inference & Deployment

The engineering stack behind production LLM serving

Training a 70B model costs millions, but serving it to millions of users introduces a different set of challenges. The same model takes 20ms to generate the first token (prefill) but can take 100x longer per subsequent token (decode) if not optimized. Understanding the inference stack — KV cache, memory bandwidth, batching, speculative decoding — is essential for anyone deploying LLMs in production.
TL;DR

LLM inference is memory-bandwidth bound, not compute bound. The KV cache grows with sequence length, consuming O(L·d·n_layers·n_heads) memory per request. Key optimizations: (1) KV cache — reuse computed K/V projections, (2) continuous batching — interleave requests at token granularity, (3) speculative decoding — use a small draft model to generate multiple tokens per forward pass, (4) prefix caching — share KV cache across requests with common prefixes. A single H100 serves ~10 concurrent requests on a 70B at 4-bit.

Autoregressive Generation

LLMs generate one token at a time. Each generated token is fed back as input for the next step:

Autoregressive Decoding: Prefill + Decode Phases

The prefill phase processes all input tokens in parallel (one forward pass). The decode phase generates tokens one at a time, each requiring a full forward pass. Decode is typically the bottleneck.

The KV Cache

The key optimization for autoregressive decoding: we cache the Key (K) and Value (V) projections from each attention layer, so they don't need to be recomputed at each step:

KV Cache Memory per Request
Memory = 2 · nlayers · nheads · dhead · L · bytes

For a 7B model (nlayers=32, nheads=32, dhead=128) at FP16:
Cache = 2 × 32 × 32 × 128 × 4096 × 2 bytes = 2 GB at 4K context
= 16 GB at 32K context

For a 70B model with 8K context: ~6 GB per request

At each decode step, we compute Q, K, V for just the new token, append K and V to the cache, then compute attention using the full cache. This avoids O(L²) recomputation per step, reducing it to O(L) per step.

The KV cache is the dominant memory consumer at long contexts. For a 70B model serving 32 concurrent requests at 128K context, the KV cache alone requires 32 × 64 GB = 2 TB of memory — far more than the model weights.

The Memory Bandwidth Wall

LLM inference is fundamentally memory-bound, not compute-bound. Each decode step reads the entire model parameters from GPU memory (HBM) into the compute units (SRAM), performs one matrix-vector multiply, and writes the KV cache:

At FP16, a 70B model is ~140 GB. On an H100 (3.35 TB/s), reading all weights takes 140 GB / 3,350 GB/s ≈ 42 ms. This sets a hard lower bound on token generation speed — ~24 tokens/second — regardless of compute efficiency.

This is why quantization speeds up inference disproportionately: at 4-bit, the 70B model is 35 GB instead of 140 GB, reducing the read time from 42 ms to 10 ms — a 4× speedup on the exact same compute operations.

Continuous Batching

Naive batching (wait for all requests to finish before starting new ones) is inefficient for LLMs because generation lengths vary widely. Continuous batching (used by vLLM, TGI) interleaves tokens from different requests at each step:

  1. System receives requests A, B, C at different times
  2. Each step: prefill new requests + decode ongoing requests in a single batch
  3. Finished requests (e.g., short generation) exit the batch immediately
  4. KV caches are paged (PagedAttention) — allocated in fixed-size blocks to avoid fragmentation and support sharing across requests with common prefixes
PagedAttention (vLLM): Inspired by virtual memory in operating systems. The KV cache is divided into fixed-size "pages." Logical pages can map to non-contiguous physical memory, eliminating fragmentation and enabling efficient sharing of common prefixes (e.g., system prompts, few-shot examples).

Speculative Decoding

A technique that generates multiple tokens per forward pass of the large model by using a small draft model:

  1. Draft model (e.g., 1B parameters) generates K candidate tokens autoregressively (fast — small model = less memory bandwidth)
  2. Large model (e.g., 70B) validates all K tokens in a single forward pass using a modified attention mask
  3. Tokens that match the large model's distribution are accepted; the rest are corrected and the process repeats

Typical acceptance rate: 70-90% with a well-aligned draft model → 2-3× throughput improvement at no loss of quality (since all outputs are validated by the large model).
