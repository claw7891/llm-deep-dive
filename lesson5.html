Inference & Deployment

The engineering stack behind production LLM serving

Training a 70B model costs millions of dollars in compute, but serving it to millions of users introduces a different set of challenges. The same model takes about 20 ms to generate the first token (the prefill phase) but can take 50–100× longer per subsequent token (the decode phase) if not optimized.

Why? Because each new token requires reading all 140 GB of model weights from GPU memory — and that memory transfer is surprisingly slow compared to how fast the GPU can compute. Understanding the inference stack — KV cache, memory bandwidth, batching, speculative decoding — is essential for anyone deploying LLMs in production.

By the end of this lesson, you'll understand why a 7B model runs easily on a laptop while a 70B needs a datacenter, and what techniques production systems use to squeeze every last token per second out of their hardware.

TL;DR

LLM inference is memory-bandwidth bound, not compute bound. The KV cache grows with sequence length, consuming O(L·d·n_layers·n_heads) memory per request. Key optimizations: (1) KV cache — reuse computed K/V projections so each step only processes one new token, (2) continuous batching — interleave requests at token granularity instead of waiting for full sequences, (3) speculative decoding — use a small draft model to generate multiple tokens per forward pass of the large model, (4) prefix caching — share KV cache across requests with common prefixes like system prompts. A single H100 serves ~10 concurrent requests on a 70B at 4-bit.

Autoregressive Generation

LLMs generate text one token at a time. Each generated token is fed back as input for the next step. This is called autoregressive generation — the model's output becomes part of its next input.

Token-by-Token Walkthrough

Let's trace what happens when generating "The cat sat on the mat":

Step-by-Step Generation
Prompt: "Translate to English: Le chat s'est assis sur le tapin"

Step 1 (Prefill): Input tokens = [Le, chat, s'est, assis, sur, le, tapin]
    → Processed in parallel (one forward pass)
    → Output: "The" (first generated token)

Step 2 (Decode): Input = [Le, chat, ..., tapin, The]
    → Full forward pass through ALL 32 transformer layers
    → Output: "cat"

Step 3 (Decode): Input = [..., The, cat]
    → Full forward pass through ALL 32 layers
    → Output: "sat"

Step 4 (Decode): Input = [..., The, cat, sat]
    → Full forward pass through ALL 32 layers
    → Output: "on"

Step 5 (Decode): Input = [..., The, cat, sat, on]
    → Full forward pass through ALL 32 layers
    → Output: "the"

Step 6 (Decode): Input = [..., The, cat, sat, on, the]
    → Full forward pass through ALL 32 layers
    → Output: "mat"

Step 7 (Decode): Input = [..., The, cat, sat, on, the, mat]
    → Full forward pass through ALL 32 layers
    → Output: "."

Result: 1 prefill step + 6 decode steps = 7 forward passes total
Each decode step is equally expensive (all 32 layers, all 70B parameters),
even though the input grew by only 1 token!

The prefill phase processes all input tokens in parallel (one forward pass). The decode phase generates tokens one at a time, each requiring a full forward pass. Decode is typically the bottleneck — it's what makes LLMs feel "slow" when you're watching them type.

Autoregressive Decoding: Prefill + Decode Phases

The KV Cache

Why This Matters

Here's the core insight: without the KV cache, every decode step would recompute attention against ALL previous tokens from scratch.

Think about generating token #4096 in a conversation. Without caching:

  • You'd compute Q, K, V for all 4095 previous tokens again
  • That's 4095 × (QKV computation) that you've already done before
  • Total complexity per step: O(L²) — quadratic in sequence length

With the KV cache:

  • For each new token, you compute only Q, K, V for that one token
  • Append the new K and V to the cache
  • Attention still considers all previous tokens (using cached values)
  • Total complexity per step: O(L) — linear in sequence length

Step-by-Step Example

KV Cache Growth (Single Head, Simplified)
Step 1 (The): compute K₁, V₁ → cache = [K₁, V₁] Step 2 (cat): compute K₂, V₂ → cache = [K₁, V₁, K₂, V₂]  attention uses K=[K₁,K₂] and V=[V₁,V₂] Step 3 (sat): compute K₃, V₃ → cache = [K₁, V₁, K₂, V₂, K₃, V₃]  attention uses K=[K₁,K₂,K₃] and V=[V₁,V₂,V₃] ... Step 4096: cache has 4096 K vectors and 4096 V vectors  attention uses all 4096 positions — O(L) work  (vs O(L²) without cache — 4096× more work!)

Without KV cache: At step 4096, you'd recompute K₁...K₄₀₉₅ from scratch.
With KV cache: You compute only K₄₀₉₆ and V₄₀₉₆. Everything else is in cache. 🎉
The saving is enormous: For a 4096-token sequence, the KV cache reduces attention computation from 4096² = 16.8M operations per layer to just 4096 per step — a 4096× reduction at the last token!

Memory Cost

The KV cache has a cost: memory. For each request, we need to store every layer's K and V projections:

KV Cache Memory per Request
Memory = 2 · nlayers · nheads · dhead · L · bytes

For a 7B model (nlayers=32, nheads=32, dhead=128) at FP16:
Cache = 2 × 32 × 32 × 128 × 4096 × 2 bytes = 2 GB at 4K context
= 16 GB at 32K context

For a 70B model with 8K context: ~6 GB per request
The KV cache dominates at long contexts. For a 70B model serving 32 concurrent requests at 128K context, the KV cache alone requires 32 × 64 GB = 2 TB of memory — far more than the model weights (35 GB at 4-bit). This is why long-context serving is expensive: each request's KV cache grows linearly with output length.

The Memory Bandwidth Wall

The Kitchen Analogy

Think of a GPU like a restaurant kitchen:

  • HBM (High Bandwidth Memory) is the pantry — it holds all ingredients (model weights), is large (80 GB on H100), but takes time to walk to.
  • SRAM is the countertop workspace — it's small (only a few MB) but extremely fast to access.
  • CUDA cores / Tensor Cores are the chefs — once ingredients are on the counter, they can cook incredibly fast.

The bottleneck in LLM inference isn't how fast the chefs can cook — it's how fast ingredients can be carried from the pantry to the counter. This is the memory bandwidth wall.

Each decode step requires reading all model weights from HBM (pantry) into SRAM (counter) to perform one matrix-vector multiply, then writing the KV cache back:

GPUMemory Bandwidth70B FP16 Read TimeCompute (1 token)
H100 SXM3,350 GB/s~42 ms~1 ms
A100 SXM2,040 GB/s~69 ms~2 ms
A100 PCIe1,555 GB/s~90 ms~2 ms
RTX 40901,008 GB/s~79 ms (24 GB < 140 GB → needs quantization)~3 ms (quantized)

At FP16, a 70B model is ~140 GB. On an H100 (3.35 TB/s), reading all weights takes 140 GB / 3,350 GB/s ≈ 42 ms. This sets a hard lower bound on token generation speed — ~24 tokens/second — regardless of compute efficiency. The chefs are idle 97% of the time, waiting for ingredients!

Why quantization speeds up inference disproportionately: At 4-bit, the 70B model is 35 GB instead of 140 GB, reducing the pantry-to-counter trip from 42 ms to 10 ms. Same chefs, same recipes — but 4× faster because the bottleneck is how fast you can carry ingredients, not how fast you can cook.

Continuous Batching

The Problem with Naive Batching

In traditional ML inference, you batch requests together and wait for all of them to finish before processing the next batch. This works for image classification (all requests take the same time) but fails for LLMs because generation lengths vary wildly.

Imagine a batch of 4 requests with lengths of 10, 50, 200, and 500 tokens. With naive batching, requests 1–3 sit idle for 490 extra steps waiting for request 4 to finish. That's 73% wasted GPU capacity.

How Continuous Batching Works

Continuous batching (used by vLLM, TGI) interleaves tokens from different requests at every single step:

  1. Step 1: System receives requests A, B, C. All are in the prefill phase — processed together.
  2. Step 2: Request A finishes generating. It exits the batch immediately. New request D joins.
  3. Step 3: Request B finishes. Request E joins. Request A's output is streamed to the user.
  4. Each step: a mix of prefilling (new requests) and decoding (ongoing requests).

Because each request is just one token per step, the batch isn't "blocked" by slow requests — every step uses the GPU for useful work.

PagedAttention (vLLM)

PagedAttention: Inspired by virtual memory in operating systems. The KV cache is divided into fixed-size "pages" (like memory pages in an OS). Logical pages can map to non-contiguous physical memory, eliminating fragmentation and enabling efficient sharing of common prefixes (e.g., system prompts, few-shot examples). Result: near-100% memory utilization vs 60-70% with naive contiguous allocation.

Speculative Decoding

A technique that generates multiple tokens per forward pass of the large model by using a small draft model to "guess" what the large model would generate.

Concrete Example

Speculative Decoding Walkthrough
Setup: Large model = 70B (slow, ~25 tok/s)
             Draft model = 1B (fast, ~500 tok/s)

Step 1: Draft model generates 7 candidate tokens in sequence:
    → ["The", "cat", "sat", "on", "the", "mat", "."] (takes ~14 ms)

Step 2: Large model checks ALL 7 tokens in one single forward pass:
    → Evaluates each position: is this what I would have generated?
    → Accepts ["The", "cat", "sat", "on", "the"] ✓
    → Rejects "mat" — large model would have said "rug" instead

Step 3: Keep the 5 accepted tokens. Reject "mat" and continue from "rug":
    → Output so far: "The cat sat on the rug"

Result: Generated 6 tokens in ~40+14=54 ms ≈ 111 tok/s
    (vs ~25 tok/s for standard decoding — 4.4× faster!)

Worst case: All 7 tokens rejected → you wasted the draft model's time.
    But you're no worse than standard decoding (still one validation pass).
Best case: All 7 accepted → 7 tokens for the price of 1 → 7× speedup!

Typical acceptance rate: 70–90% with a well-aligned draft model → 2–3× throughput improvement at no loss of quality (since all outputs are validated by the large model before being emitted).

Key insight: Speculative decoding works because most token predictions are "easy" — the next word is often obvious from context. The draft model handles the easy cases cheaply, and the large model only needs to check them. The large model's expensive compute is reserved for verification and for the hard cases where the draft model guessed wrong.

vLLM in Practice: A Concrete Calculation

Let's put everything together with a real-world capacity planning example:

Serving 32 Concurrent Requests on a 7B Model
Model: Llama 3 7B, INT4 quantized
Concurrent requests: 32
Context length: 4,096 tokens each

Memory budget:
  Model weights (INT4): 7B × 0.5 bytes = 3.5 GB
  KV cache (32 reqs × 4K context): 32 × 2 GB = 64 GB
  Activations + overhead: ~2.5 GB
  Total: ~70 GB

Result: Fits on 1 × A100-80GB.

Notice: The KV cache (64 GB) dominates the memory budget — it's 18× larger than the model weights (3.5 GB)! This is typical for production deployments.

Now for a 70B model with the same setup:

Serving 32 Concurrent Requests on a 70B Model
Model: Llama 3 70B, INT4 quantized
  Model weights: 70B × 0.5 bytes = 35 GB
  KV cache (32 reqs × 4K context): 32 × 6 GB = 192 GB
  Activations + overhead: ~5 GB
  Total: ~232 GB

Result: Need 3–4 A100-80GB GPUs (model parallelism + KV cache sharding).

This is why large models are expensive to serve — the KV cache scales with both
concurrency AND context length.

Summary

  • Autoregressive generation processes one token at a time. Each decode step is a full forward pass through all layers, making inference memory-bandwidth bound.
  • KV cache avoids recomputing attention projections for previous tokens, reducing complexity from O(L²) to O(L) per step — essential for long sequences.
  • Memory bandwidth wall is the fundamental bottleneck: reading model weights from GPU memory dominates inference time, not computation. Quantization directly alleviates this.
  • Continuous batching interleaves requests at each token step, eliminating GPU idle time from variable-length generations.
  • Speculative decoding uses a small draft model to generate multiple candidates, verified in one pass by the large model — achieving 2–3× throughput without quality loss.
  • KV cache dominates deployment costs: for 32 concurrent requests at 4K context, the cache is 18× larger than the model weights. This is the primary scaling consideration for production systems.
