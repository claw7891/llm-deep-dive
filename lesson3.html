Training & Pretraining

Training objectives, data pipelines, training dynamics, compute budgets, and what can go wrong

Pretraining an LLM is the largest engineering effort in machine learning. A single training run on a 70B-parameter model consumes thousands of GPUs for months, costs tens of millions of dollars, and processes trillions of tokens. Understanding the training process is essential for knowing what these models actually learn — and what they miss. Let's walk through everything with concrete examples.
TL;DR

LLMs are trained on trillions of tokens of internet text using next-token prediction (autoregressive language modeling). The loss is cross-entropy between predicted and actual next token. Training uses distributed data parallelism across thousands of GPUs, AdamW optimizer with cosine learning rate schedule, and gradient clipping. Data quality matters as much as quantity — deduplication, filtering, and curation are critical. Compute cost roughly follows 6·N·D FLOPs.

The Core Idea: Guessing the Next Word

Imagine you're reading a book where the last word of every sentence is covered with a sticky note. Your job is to guess that word:

"The cat sat on the [???]"
"She opened the door and walked [???]"
"Python is a popular programming [???]"

You'd guess "mat", "in", and "language" respectively. That's exactly what an LLM does during pretraining — but with trillions of sentences from the internet, books, and code.

The model sees the tokens up to position t and must predict the token at position t+1. It starts terrible (random guesses) and over trillions of examples gradually learns the statistical patterns of language: grammar, facts, reasoning, style, everything.

Pretraining Objectives

Autoregressive / Causal Language Modeling

The dominant objective for generative LLMs (GPT, LLaMA, etc.). Given a sequence of tokens x₁, x₂, ..., xₙ, maximize the probability of each token given all previous tokens:

Autoregressive LM Objective
L = −Σt=1T log P(xt | x1, x2, ..., xt−1)

This is simply the negative log-likelihood of the entire sequence under the model. Minimizing this loss is equivalent to maximizing the probability the model assigns to the training data.

Concrete Example: Next-Token Prediction

Let's trace a tiny example. Suppose our model has a vocabulary of just 5 words: {"the", "cat", "sat", "mat", "."}. Given input "The cat sat on the", the model needs to predict the next token. Let's say the correct answer is "mat".

// Input: "The cat sat on the" → model produces logits (raw scores)
logits = ["the": -1.2, "cat": -3.5, "sat": -2.8, "mat": +2.1, ".": -0.5]

// Softmax converts to probabilities
probs = ["the": 0.04, "cat": 0.01, "sat": 0.01, "mat": 0.89, ".": 0.05]

// The correct answer is "mat" (index 3). Loss = -log(0.89) ≈ 0.12
// If the model were wrong (e.g., "the": 0.78, "mat": 0.02), loss = -log(0.02) ≈ 3.91

The model processes every position simultaneously (thanks to causal masking), computing a loss at each position. For the sentence "The cat sat on the mat" (6 tokens), it computes losses at 5 positions (no loss for the first token):

Context Target Model Prediction Loss
[The]catP(cat|The)=0.450.80
[The, cat]satP(sat|...)=0.520.65
[The, cat, sat]onP(on|...)=0.380.97
[The, cat, sat, on]theP(the|...)=0.610.49
[The, cat, sat, on, the]matP(mat|...)=0.890.12
Total loss for this sentence: 0.80+0.65+0.97+0.49+0.12 = 3.03

The loss for each training batch (typically 2M-4M tokens across all sequences) is averaged, and the gradient is computed to update model parameters. The model never "knows" the correct answer in advance — it can only use context to the left for each position.

Why Cross-Entropy?

Cross-entropy measures how wrong your probability distribution is.

Let's say your model produces probability P = [0.04, 0.01, 0.01, 0.89, 0.05] over 5 vocabulary words, and the correct answer is index 3 ("mat"). Cross-entropy is:

H(P, true) = −log(P[3]) = −log(0.89) ≈ 0.12

Why does this make sense?

• If the model assigns 90% to "mat" → loss is low (~0.10). The model is confident and correct.
• If the model assigns 0.1% to "mat" and 50% to "stove" → loss is high (~6.9). The model is confident about the wrong answer — heavily penalized.
• If the model is unsure but close — 30% to "mat", 30% to "rug", 20% to "floor" → loss is about 1.2. Not great but not catastrophic.

The model learns to shift probability mass away from wrong answers and toward the correct one. Over trillions of training tokens, this forces the model to learn the intricate patterns of language.

Masked Language Modeling

Used by BERT and other encoder-only models. Randomly mask 15% of tokens and predict them from bidirectional context:

L = −Σt ∈ masked log P(xt | x≠t)

Unlike autoregressive modeling, masked LM uses both left and right context to predict the masked word. Input: "The [MASK] sat on the [MASK]" → output: "cat", "mat". This is great for understanding but can't generate text (you can't produce a sequence left-to-right with bidirectional masks).

Data Curation Pipeline

Raw internet text is noisy, duplicated, and often low-quality. Modern pretraining pipelines apply extensive filtering. Data quality is as important as data quantity.

DeduplicationRemove near-duplicate documents (MinHash LSH), duplicate n-gram sequences
Quality filteringHeuristic rules (perplexity thresholds), classifier-based (fastText, CCNet), domain filtering
Toxicity / SafetyBlocklist URLs, hate speech classifiers, PII redaction
Data mixingWeighted sampling: web text + books + code + academic papers

Why Deduplication Matters — A Concrete Example

Imagine you're training on a raw crawl of the web. Without deduplication:

⚠️ The Problem
A single Wikipedia article "History of the French Revolution" might appear once on Wikipedia, but be copied verbatim on 50 different blog sites, 3 essay databases, and 2 forum threads. Without deduplication, that article is effectively seen 56 times — it gets 56× more training weight than it deserves.
✅ The Solution: MinHash LSH
MinHash converts documents into compact "fingerprints" (sets of hash values). Two news articles about the same event by different outlets will have similar fingerprints. Locality-Sensitive Hashing (LSH) groups documents with fingerprint similarity > 0.8 (or whatever threshold) — these are flagged as near-duplicates. Only one copy is kept.
The Scale
Deduplication typically removes 30-50% of raw CommonCrawl data. The LLaMA 3 dataset started from ~50T tokens of raw web text and was deduplicated down to ~15T tokens. The removed data wasn't adding information — it was just repetition.

Data Quality Filtering

The LLaMA 3 dataset (15T+ tokens) was curated by training a small language model (a tiny transformer) to score document quality. Documents that looked like coherent English text (low perplexity to a reference model) scored higher. Low-quality pages (SEO spam, auto-generated content, gibberish) scored low and were discarded or downsampled.

Common quality heuristics include:

  • Perplexity threshold: run a small reference LM on the document; discard if perplexity is too high (too much noise)
  • Character-to-word ratio: pure spam often has unusual ratios
  • Minimum document length: discard pages under 50 words
  • Language ID: filter to target languages (English, etc.)
  • URL blocklist: known spam domains

Note that books and Wikipedia are seen for multiple epochs (2-3 passes), while web data and code are seen for just over 1 epoch. High-quality sources get repeated exposure; lower-quality web text gets a single pass.

Training Optimization

Optimizer: AdamW

AdamW is the standard optimizer for LLM training. It combines momentum (for fast convergence) with adaptive learning rates (for handling sparse gradients) and decoupled weight decay:

AdamW Update (per parameter θ)
mt = β₁ · mt−1 + (1 − β₁) · gt   (biased first moment — "momentum")
vt = β₂ · vt−1 + (1 − β₂) · gt²   (biased second moment — "velocity")

m̂t = mt / (1 − β₁ᵗ)   (bias correction)
v̂t = vt / (1 − β₂ᵗ)   (bias correction)

θt = θt−1 − η · m̂t / (√v̂t + ε) − λ · η · θt−1
Intuition for AdamW terms:
• Momentum (mt): If the gradient has been consistently pointing in one direction, accelerate in that direction. Like a ball rolling down a hill — it builds speed.
• Velocity (vt): Parameters with consistently small gradients get larger updates (higher learning rate). Parameters with large, noisy gradients get smaller updates. This adapts the learning rate per-parameter.
• Weight decay (λ·η·θ): Gently pushes all weights toward zero, preventing any single parameter from growing too large and dominating. This is a simple but effective regularization.

Typical hyperparameters: β₁ = 0.9, β₂ = 0.95, ε = 10⁻⁸, weight decay λ = 0.1

Learning Rate Schedule: Cosine Decay with Warmup

The learning rate follows a cosine curve: linear warmup from 0 to max_lr over the first ~2,000 steps, then cosine decay to ~10% of max_lr over the remaining steps:

η(t) = ηmax · ½(1 + cos(π · t / T))   (after warmup)
Why this schedule?

• Warmup (first ~2,000 steps): Early in training, the model is random and gradients are chaotic. Jumping straight to a high learning rate would cause divergence — parameter updates would be too large and the loss would explode. Warmup lets the model stabilize first.

• High LR (early training): Fast exploration of the loss landscape. The model quickly learns broad patterns.

• Low LR (late training): Fine-grained convergence. Small updates let the model "settle" into a good minimum without overshooting. The LR doesn't go to zero — it stays at ~10% of max to allow continued learning.

Think of it like a search: first you run fast to find promising areas, then you slow down to explore the details of the best area.

Batch Size Scaling

LLM training uses very large batch sizes (millions of tokens per batch) and scales the learning rate with batch size:

η(B) = ηref · √(B / Bref)   (sqrt scaling for large batches)

Larger batches give more accurate gradient estimates, allowing a larger learning rate. LLaMA 2 70B trained with a batch size of 4M tokens across 2,000 GPUs. Each step processes 4M tokens, and the model saw 2T tokens total → 2T / 4M = 500,000 training steps.

Compute Budget

Training compute is measured in FLOPs (floating-point operations). For a forward and backward pass on a single token with a dense transformer:

Training Compute (Kaplan et al. 2020)
Ctrain ≈ 6 · N · D

Where N = number of parameters, D = number of training tokens.

The factor 6 comes from:
• Forward pass: ~2 FLOPs/parameter/token
• Backward pass (gradients): ~4 FLOPs/parameter/token
• Total: 2 + 4 = 6

Making Compute Tangible: A Numerical Example

Training LLaMA 2 70B (70 billion parameters, 2 trillion tokens)
1. Total FLOPs needed: C = 6 × 70×10⁹ × 2×10¹² = 8.4 × 10²³ FLOPs

2. GPU capability: An NVIDIA H100 GPU provides ~1979 TFLOPS (1.98 × 10¹⁵ FLOPs/second) for FP16

3. Single-GPU time: 8.4 × 10²³ / 1.98 × 10¹⁵ ≈ 424 million GPU-seconds

4. Convert to human units:
    • 424M sec / 3600 ≈ 118,000 GPU-hours
    • 118,000 / 24 ≈ 4,900 GPU-days
    • 4,900 / 365 ≈ 13.4 GPU-years

5. With parallelism: If you have 2,000 H100 GPUs running in parallel, that's:
    • 118,000 / 2,000 ≈ 59 hours ≈ 2.4 days

6. Realistically, with parallelism overhead (communication, pipeline bubbles, failures), expect about 2-3× this time. The actual LLaMA 2 70B training took 21 days on 2,000 A100 GPUs (A100s are about 40% slower than H100s).

Distributed Training

Training a 70B model requires more memory than a single GPU can hold. A single A100 has 80GB of memory; a 70B model in FP16 needs 140GB just for weights — let alone optimizer states and gradients. Three levels of parallelism are combined:

Distributed Training — How Gradients Are All-Reduced Across GPUs

Three Levels of Parallelism

  • Data parallelism — Each GPU processes different micro-batches. After each step, gradients are averaged (all-reduce) across all GPUs. Every GPU ends up with the same weight update. Simple and effective for models that fit on one GPU.
  • Tensor parallelism — Individual matrix multiplies (like Q·KT for attention) are split across GPUs. Each GPU handles a slice of the weight matrix. This reduces memory per GPU at the cost of extra communication. Standardized in Megatron-LM.
  • Pipeline parallelism — Different layers are assigned to different GPUs (GPU 0 has layers 1-10, GPU 1 has layers 11-20, etc.). This reduces memory but introduces idle time ("pipeline bubbles") as the pipeline fills and drains. Optimized with the 1F1B (one forward, one backward) schedule.

ZeRO (Zero Redundancy Optimizer)

ZeRO eliminates redundant copies of data across GPUs.

In standard data parallelism, each GPU stores a complete copy of parameters, gradients, and optimizer states. For a 70B model in FP16:

Parameters: 140GB + Gradients: 140GB + Optimizer states: 280GB = 560GB per GPU
That's 7x what a single A100 (80GB) can hold!

ZeRO Stage 1: Shard optimizer states across GPUs — memory drops to ~340GB/GPU
ZeRO Stage 2: Also shard gradients — memory drops to ~200GB/GPU
ZeRO Stage 3: Also shard parameters — each GPU only stores ~16GB of model data, enabling 100B+ models on thousands of GPUs with near-linear scaling efficiency.

Convergence & Loss Curves

During training, the loss decreases following a power law with the number of tokens seen. A typical training run shows smooth decay with occasional spikes from data quality issues or numerical instability:

Scaling relationship during training
L(D) ≈ L∞ + A · D−α

Where:
L(D) = loss after D tokens of training
L∞ = irreducible loss (entropy of natural language)
A, α = constants (α ≈ 0.1-0.3 for most LLMs)

The loss curve tells you a lot about training health: a smooth downward trend means training is proceeding normally. Spikes or plateaus indicate problems.

What Can Go Wrong

Training a massive LLM is hard. Here are the most common failure modes and how they're handled:

Problem Cause Solution
Loss spike Bad batch of data (corrupted tokens), numerical overflow Skip the spike batch, reduce learning rate temporarily, restore from checkpoint before spike
NaN / Inf loss Gradient explosion, division by zero in LayerNorm, softmax overflow Gradient clipping (max norm = 1.0), increase ε in LayerNorm, reduce batch size
Loss divergence Learning rate too high, bad initialization, corrupted checkpoint Lower learning rate, restore from known-good checkpoint, add warmup
Loss plateau Model capacity exhausted, bad data mix, stuck in local minimum Increase LR, add data variance, adjust batch size (sometimes increasing batch helps)
Hardware failure GPU crashes, network timeouts, memory errors (common at 2000+ GPU scale) Frequent checkpointing (every 30-60 minutes), automatic failure recovery, redundant GPUs
At the scale of a major LLM training run, hardware failures are inevitable. With 2,000 GPUs running for weeks, you'll lose GPUs daily. Training frameworks must be designed to handle this: checkpoint frequently, detect failures, and restart from the last good checkpoint. The industry standard is to checkpoint every 30-60 minutes, which costs ~2-3% of total training time but prevents catastrophic restart-from-scratch scenarios.

Gradient clipping (|g| ≤ 1.0), learning rate warmup, and skipping problematic batches all help maintain stable training curves. Modern training frameworks (NeMo Megatron, DeepSpeed, torch FSDP) are battle-tested against these failure modes.

Summary

  • Core task: next-token prediction — "What word comes next?" on trillions of examples
  • Loss function: cross-entropy — penalizes wrong confident predictions heavily
  • Data curation: deduplication removes 30-50% of raw web data; quality filtering ensures coherent training
  • Optimizer: AdamW — momentum + adaptive learning rates + weight decay
  • LR schedule: warmup → cosine decay — fast exploration, then fine convergence
  • Compute: 6·N·D FLOPs — LLaMA 2 70B needs ~8.4×10²³ FLOPs (2 days on 2000 H100s)
  • Distributed training: data + tensor + pipeline parallelism + ZeRO
  • Failure modes: loss spikes, NaN, divergence, hardware failure — handled with checkpointing, gradient clipping, and careful LR management
